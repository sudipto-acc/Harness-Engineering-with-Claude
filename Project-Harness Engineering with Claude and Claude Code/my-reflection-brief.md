### System 1 — Agentic loop

1. **Loop control.** Quote the `stop_reason` sequence from one trace. Name the file and function that decides continue-vs-stop, and how.
   The decision is made in `claims_intake/loop.py`, function `run()`: a `while True` loop whose only exits are `stop_reason == "end_turn"` (return `FinalState`), `"tool_use"` (execute every `tool_use` block, append one `user` turn holding all the `tool_result`s, `continue`) and anything else (`raise UnexpectedStopReason`); `Budget.check()` at the top of each turn is only the safety net. `test_loop_continues_on_tool_use` pins the sequence `["tool_use", "end_turn"]` and `test_loop_raises_on_unexpected_stop_reason` pins `max_tokens` -> raise, and the AST audit `test_stop_reason_is_loop_control` checks the loop really exits through `stop_reason` (all PASSED in `evidence/system1_agentic_loop/pytest_S1.log`). In my live run `claim_04_neighbor_injury` (run `20261102_043419`, `evidence/system1_agentic_loop/claim_04_neighbor_injury.jsonl`) the sequence was `tool_use, tool_use, tool_use, end_turn`: turn 1 looked up the policy and recorded six facts, turn 2 called `classify_claim` (liability, 0.95) and `assess_severity` (high), turn 3 called `route_to_adjuster`, and turn 4 was the closing confirmation with no tool calls. `claim_01_kitchen_fire` (`claim_01_kitchen_fire.jsonl`) ended `tool_use, tool_use, end_turn` after only recording facts, which the loop correctly treated as the end of the model's turn (see answer 4).

2. **Anti-pattern.** Name one anti-pattern `test_antipatterns.py` checks for. What would break in your run if the loop used it?
   `test_no_integer_literal_iteration_cap_in_loop` forbids `for _ in range(<int>)` and `while turn < <int>` as the stopping mechanism, and its sibling `test_no_string_membership_against_text_in_loop` forbids `"done" in text` style control flow; both PASSED (`evidence/system1_agentic_loop/pytest_S1.log`). A literal cap would end a claim mid-work: the agent needs `lookup_policy`, fact recording, an optional `request_clarification`, `classify_claim`, `assess_severity` and a terminal tool, so a cap below the turns the model really uses leaves the claim neither routed nor escalated. That is why the loop relies on a `Budget` (defaults in `run.py`: 500,000 input tokens and 180 s per claim) that raises `BudgetExceeded` instead of truncating (`test_budget_raises_when_token_cap_exceeded`), and why `run.py` has the `_escalate_without_terminal` backstop (`test_claim_without_terminal_tool_is_escalated`). In my `summary.md` the claims took 2 to 4 turns (2 turns for `claim_02`, `claim_03` and `claim_07`; 4 for `claim_04`, `claim_05` and `claim_08`), so a small literal cap such as 3 would have cut `claim_04` and `claim_05` before the closing turn and `claim_08` before any terminal action, with the cap, not the model, deciding the outcome.

3. **Tool design.** Pick two tools with overlapping inputs. How do the descriptions prevent misrouting? What did a structured tool error let the agent do that a generic string would not?
   `route_to_adjuster` and `escalate_to_human` take overlapping inputs (a claim summary plus case facts) and both end the claim, so their descriptions in `claims_intake/tools.py` give them complementary triggers: route is for classification confidence of at least 0.6 once severity has been assessed, escalate is for confidence below 0.6 even after clarification or a claim that cannot be routed safely (multiple plausible types, missing critical facts, policy disputes), and both are labelled `TERMINAL TOOL` and "call exactly once". The "pick exactly one" rule is in the system prompt and is also enforced in code: `queue` is an `enum` of the four claim types (`test_categorical_fields_use_enums`), routing before `classify_claim` or `assess_severity` returns an error (`test_routing_requires_classification_and_severity`), and a second terminal call returns `terminal tool already called this claim` (`test_double_terminal_is_graceful_error`). Errors are structured as `{"is_error": true, "error_category": "transient"|"permanent", "is_retryable": bool, "message": ...}`, so the model can tell "fix the order of my calls" (permanent, the message names the missing step) from "try the same call again" (transient, `test_handler_exception_is_caught_as_transient_error`), which a generic `"error"` string cannot express. All of these are PASSED in `evidence/system1_agentic_loop/pytest_S1.log`.

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
    `evidence/system4_orchestration/run-shift-windowed.log` (`--since 2026-04-01T00:00:00Z`) reports `shift C: 17 new defects`, and `extras.log` shows the warm tier holds **40** rows, so the model's prompt is built from 17 of 40. The README-style run with the default 8-hour window returns 0 (`shift_run_output.txt`) because the fixture ends on 2026-04-29. The indexed query is `WarmStore.defects_since`, `SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?`, and `EXPLAIN QUERY PLAN` reports `SEARCH defects USING INDEX idx_defects_ts (ts>?)` (`extras.log`; `test_defects_since_uses_index_and_does_not_load_full_table`). `pipeline.gather_new_defects` is a pure pass-through to SQL with `limit=50` (`test_gather_new_defects_has_no_python_side_filtering`) and the rich prompt must stay under 4,000 characters (`test_build_rich_prompt_stays_under_4000_chars`), so the model only ever sees the hot state plus at most 50 recent rows and the prompt does not grow with history.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?
    `shift_monitor/recovery.py` `decide()` returns `fresh` for an empty or already-complete manifest, and for an incomplete one returns `resume` only if the last step is at most `STALE_RESUME_THRESHOLD_MINUTES = 30` old (about 1/16 of an 8-hour shift), otherwise `fresh`. In my run (`evidence/system4_orchestration/extras.log`) a last step 10 minutes ago gave `resume`, 45 minutes ago gave `fresh`, a complete manifest gave `fresh` and an empty manifest gave `fresh`; the boundary is pinned by `test_recovery_decide_truth_table[30-False-resume]` and `[31-False-fresh]` (`pytest_S4.log`). A stale partial session carries assumptions about a working set that has since moved on, so resuming it can replay outdated context; a fresh invocation rebuilds the prompt from the current hot state and warm-tier rows, and the `resumed` shape (`invocation.resumed`) injects only the manifest's prior partial findings plus the defects since the last step, which is shorter, current and checkable. The findings themselves survive the crash because `Manifest.append_step` writes one fsynced JSON line per step.

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?
    My final `hot_state.json` is **965 bytes** (`evidence/system4_orchestration/hot_state.json`; size line in `extras.log`) against `HOT_STATE_BYTE_BUDGET = 5,120`. The budget is enforced three ways: the pydantic `HotState` caps `recent_defect_hashes` at 20 (`test_hotstate_rejects_more_than_20_hashes`), `write_atomic` raises if the payload is over budget, and `pipeline._trim_to_budget` drops trailing alerts first. The hot state is pasted into every prompt (`invocation.rich`), so any growth per shift is paid again on every future shift; a bounded block means the 1,000th shift costs about what the first one did instead of drifting toward the context limit, and the history stays in the warm and cold tiers.

15. **Deterministic vs prompt.** Cite one behavior guaranteed in code (terminal tool, read-only allowlist, atomic write, byte budget) and one guided by prompt. When is each right?
    Guaranteed in code: `HotState.write_atomic` writes a temp file, `fsync`s and `os.replace`s it, and raises if the payload exceeds 5,120 bytes, so state is never half-written or oversized (`test_hotstate_atomic_write`; my `hot_state.json` is 965 B). Likewise `run.py` `_escalate_without_terminal` guarantees every claim ends routed or escalated even if the model forgets a terminal tool (`test_claim_without_terminal_tool_is_escalated`). Guided by prompt: `claims_intake/system_prompt.py` tells the model to ask at most one clarifying question per missing fact and to route only at confidence of at least 0.6; the model can ignore that, which is why the code backstop exists. Use code where a failure is unacceptable or irreversible (state integrity, termination, write access), and prompt where the decision is judgment that cannot be enumerated (classification, whether a question is worth asking), with a guard behind it.

16. **Context, two faces.** Compare context management in System 2 (intra-session) and System 4 (cross-session) with cited numbers from both. Same principle, different mechanism — how?
    System 2 manages context inside one long session: the 48-turn transcript is 38,708 tokens, of which the active issue is kept byte-exact (15,789 tokens) and the two resolved issues are summarized to 412 and 425 tokens, with a 204-token case-facts block on top, for 16,812 assembled tokens (`evidence/system2_context_strategy/budget.json`, a 56.57% reduction). The mechanism differs: System 2 compresses prose with a summarizer inside the session, while System 4 never asks the model to summarize history and instead tiers state (hot, warm, cold) and pre-filters with an indexed query.

    My first System 4 run exited 0 and all 33 tests passed (`evidence/system4_orchestration/first-try-default-encoding/pytest.log`), yet `hot_state.json` was wrong: the three `active_alerts` contained `â€”` where the recorded response has an em dash (`first-try-default-encoding/hot_state.json`, 658 B). 20. **What you'd change.** One architectural decision you'd make differently, grounded in what you observed.
    I would make the harness verify what it persists instead of trusting default file I/O: pass `encoding="utf-8"` explicitly where System 4 reads the recorded response (`__main__._build_client`), and read the written `hot_state.json` back and compare it with the proposed state before reporting success.
